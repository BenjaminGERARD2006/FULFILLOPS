# ADR-001: Use PostgreSQL as the shared transactional store and durable work table

- **Status:** Accepted as the current team design; validate during worker integration.
- **Date:** 12 November 2026
- **Owners:** Student 1 (API/database); review with Students 2 and 3 during integration.

## Context

FulfillOps must accept orders quickly, reserve inventory atomically, persist an idempotency mapping, and make accepted work durable before returning HTTP `202`. The worker runs separately and must recover abandoned work after a process restart. Multiple API and worker instances must share authoritative state. A database transaction must not leave partial stock reservations or an accepted order without its durable work record.

## Decision

Use PostgreSQL 16 as the authoritative relational store and as the durable work table. FastAPI uses SQLAlchemy 2 for database access, and Alembic versions the schema. The API creates the order, order items, idempotency record, inventory decrements and one `jobs` row in one transaction. No separate Redis broker is required for the current design.

The current schema uses:

- `products` and `inventory` for catalog and available stock;
- `orders` and `order_items` for accepted business orders;
- `idempotency_records` for durable replay detection;
- `jobs` for durable worker work, attempts, scheduling, leases and dead-letter state.

## Consequences

### Benefits

- A single PostgreSQL transaction can commit the inventory reservation and durable work record together.
- Inventory and idempotency state are shared across API replicas; they are not held in process-local memory.
- PostgreSQL constraints and conditional updates enforce important invariants.
- A separate broker and its operational configuration are avoided for this project.
- The `jobs` table can support concurrent workers with transactional claims and row locking.

### Costs and risks

- The worker team must implement safe atomic job claiming, leases, expired-lease recovery, bounded retries and dead-letter handling correctly.
- Long-running work must not hold a database transaction or row lock for the entire external processing duration; use a short claim transaction and a lease.
- At-least-once delivery means the worker's business-side effect must be idempotent.
- PostgreSQL is now both the business data store and work queue, so database availability and capacity affect both API acceptance and background processing.

## Required validation

- Demonstrate two workers claim different jobs without double-claiming a live lease.
- Kill a worker after a job is claimed; prove the expired lease is recovered and the order completes without a duplicate business effect.
- Demonstrate bounded retry/backoff and persistent dead-letter/operator-review state.
- Restart API and worker processes and prove orders and idempotency records survive.
- Run the public checker, including concurrency and stress modes, against a freshly seeded isolated test database.

## Alternatives considered

- **PostgreSQL plus Redis Streams:** not selected because it introduces a second durable system and additional deployment/operations work that is not necessary for the current project's requirements.
- **In-memory queue or process-local idempotency:** rejected because state would be lost on restart and would not coordinate multiple API/worker instances.
- **Synchronous processing inside the API request:** rejected because the contract requires a separate worker and an acceptance response before worker processing.
